# QA checklist

- Confirm the target PrestaShop track and declared PHP compatibility.
- Confirm entrypoints stay thin and new business logic is in focused, testable classes.
- For service wiring changes, check placement and imports against `CONVENTIONS.md` (Hooks and dependency injection). Verify dependency resolution and the affected runtime paths in each intended admin/front container, including context-specific PrestaShop implementations; confirm context-only services are not registered in the opposite container. Report unavailable runtime checks explicitly.
- Confirm global identifiers are module-prefixed and have a canonical owner; configuration uses its typed façade and explicit scope.
- For new or changed shared contracts, identify the owner/source and search the affected scope for old/new values and symbolic references. Confirm production consumers reuse the source and semantically different values remain separate; classify and justify retained copies under `CONVENTIONS.md` (Canonical sources for shared contracts).
- Verify required platform representations and documented cross-module mirrors agree with their owner; run applicable consistency/contract checks, regenerate generated files, and update affected documentation. Preserve historical migration meaning and verify affected upgrade paths.
- Confirm contract tests use independent expectations where needed to catch an incorrect canonical value. At handoff, name the canonical source, report search/check limitations, and state whether unjustified production duplication remains.
- Confirm every admin route/action has the correct ACL, HTTP method, CSRF behavior, route constraints, and installed visible/hidden tab mapping.
- For new or redesigned admin forms, verify the Symfony controller/form path, native Twig layout and form theme, field types, field-level help/errors and standard controls against `CONVENTIONS.md` (Forms and native PrestaShop UI). Record any deliberate legacy compatibility exception.
- Exercise changed multistore forms in all-shops, group and shop contexts, and with multistore disabled. Check inherited disabled fields, enabling an override, saving it, the global per-field override dropdown, and unchecking an override to restore inheritance. Confirm changes stay in the intended scope and parent changes preserve child overrides.
- Verify cleared multi-selects, unchecked boolean settings, explicit empty/false overrides, reload after save, and validation failures. Confirm submission semantics do not confuse an omitted/disabled field with a deliberate clear. For configuration migrations, check that existing scoped values survive even when multistore is disabled.
- For front-office forms, verify the active theme's native layout and controls, account breadcrumb and return links, styled checkboxes, editable textarea appearance, field-level help/errors, retained input after validation failure and customer-facing wording.
- Visually inspect changed admin/front forms in each supported PrestaShop version and declared theme, including a narrow viewport and keyboard interaction. Open choice widgets and toggle applicable overrides; check native styling, loaded assets and absence of duplicate JavaScript initialization. Successful HTML rendering or HTTP tests alone do not establish correct appearance or widget behavior.
- Run PHP syntax checks and Composer validation/autoload generation where applicable.
- Run the module's lint/style checks, Autoindex, and automated tests.
- Apply CONVENTIONS.md (Human-readable source and formatting): check naming, focused functions, control flow, comments and error paths as well as automatic formatting.
- Verify the project-local formatter version/configuration, documented write/check commands and CI enforcement. Run the non-mutating format check before tests/review; report its actual outcome and unsupported-language gaps.
- Confirm formatting preserves generated resources, historical evidence and dependencies; inspect normalization separately from behavior changes. Verify formatter tooling/configuration and node_modules are absent from the installable ZIP.
- Require tests for every new module and focused or regression tests for changed business behavior.
- If installation, schema, ObjectModel/ORM mapping, configuration, hooks, translations, or multistore behavior changed, verify the relevant install/upgrade and runtime paths.
- Confirm unique constraints/indexes match invariants and query paths; confirm no hardcoded shop/language/entity IDs.
- Confirm monetary decisions avoid floats and stored operational timestamps use UTC.
- Build and test the final production artifact after dependency scoping; confirm no development packages or obsolete Avalanche wrapper packages were added.
- Complete CHECKLIST_LEGAL.md against the final artifact and intended distribution. Required notices/licenses are production content. Unresolved license/provenance obligations block release; an inventory or dependency scanner alone is not approval.
- Validate the actual installable ZIP against the explicit runtime allowlist in CONVENTIONS.md (Composer and packaging), including hidden files and bundled dependencies. Confirm development/AI documentation, tests, tools, environment files, backups, working data and secrets are absent, while required runtime/install/upgrade files and mandatory licenses/notices remain.
- Check the module root and every directory in the extracted ZIP for `index.php`, including dependency directories; verify existing functional entrypoints were preserved. Exercise directory creation during installation/upgrades/runtime and verify guards are created before private data is written.
- Record the private-directory HTTP checks from CHECKLIST_SECURITY.md against the extracted artifact in an isolated environment. Missing guards, missing required access-denial files, prohibited package contents, or failed/unperformed required protection checks block release.
- For API/cron changes, verify timeouts, TLS, retry bounds, locks, idempotency, batching/deadlines, summaries, and operational state.
- Confirm English source strings and matching `cs-CZ` and `sk-SK` XLF entries.
- Report checks that ran and checks that could not run; do not describe inspection as execution.
- Verify no unrelated runtime, configuration, schema, or documentation changes.
